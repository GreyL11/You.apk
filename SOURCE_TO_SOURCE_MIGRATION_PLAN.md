## MEDIAPIPE RULE — explicit finding

**Legacy uses**: `@mediapipe/tasks-vision` (vendored in `www/vendor/tasks-vision.mjs`), specifically `PoseLandmarker` (BlazePose-family, 33-landmark topology) for training and `FaceLandmarker` + `ImageSegmenter` for the face subsystem — confirmed from `www/pose.js`/`www/face/model.js` in the prior audit pass and this session's own review of `www/face/*`.

**Android uses**: `com.google.mlkit:pose-detection`/`pose-detection-accurate` and `com.google.mlkit:face-detection` (confirmed directly in `app/build.gradle.kts`) — Google ML Kit's own pose/face models, a **different model family** than MediaPipe Tasks' BlazePose/FaceLandmarker, with a different landmark set and indexing.

**This substitution happened without documented justification**, and it matters because:
- Google **does** officially publish `com.google.mediapipe:tasks-vision` for Android (the same underlying task API the legacy web app uses, just the native Android artifact instead of the JS/wasm one) — this was not evaluated or ruled out anywhere in the project's history that I could find.
- Every joint-angle threshold ported into `Exercises.kt`/`RepCounter.kt` (`HYSTERESIS=12°`, `MIN_RANGE_DEG=25°`, etc.) was tuned against BlazePose's specific landmark geometry. ML Kit's pose model has different joint definitions and confidence semantics; there is no verification anywhere in this codebase that these thresholds mean the same thing against ML Kit output as they did against MediaPipe output.
- **Recommendation**: before investing further in `RepCounter.kt`/`Exercises.kt`, either (a) switch to `com.google.mediapipe:tasks-vision` for Android to preserve the actual behavioral contract the legacy thresholds were built for, or (b) if ML Kit is kept for a deliberate platform reason (smaller APK, tighter Play Services integration, etc.), **re-derive and re-validate every threshold against ML Kit's landmark output** rather than assuming the legacy numbers transfer. Do not claim parity on rep-counting accuracy until one of these two things happens — right now neither has, and the single test that exists for this area (`ExercisesTest.kt`) only checks that constants equal themselves, so a silent mismatch would not be caught.
